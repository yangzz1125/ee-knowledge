## 1. 设计目标

本项目只服务于“电磁场与波”这一门固定课程。知识图谱内容由项目开发者人工编写和检查，不包含教材上传、文档解析、自动知识抽取和教材来源管理。

本数据结构需要支持：

- 按章节组织知识；
- 搜索概念、物理量、定律、公式、方法和应用；
- 表达知识实体之间的有向或无向关系；
- 查询一个实体的相邻知识；
- 查询两个实体之间的关系路径；
- 展示公式、变量、单位和成立条件；
- 为知识图谱 RAG 提供结构化检索上下文；
- 在不改变前端接口的情况下替换底层存储方式。

## 2. 设计原则

### 2.1 领域对象与存储技术分离

本文件首先定义业务数据结构，不让对外接口依赖具体存储实现。由于课程知识固定、规模小且以读取为主，MVP 和正式版均使用单个 JSON 文件保存知识库，后端启动时一次性校验并加载到内存。若未来项目范围变化，仍可在不修改前端接口的情况下替换存储方式。

### 2.2 内部标识与显示文字分离

知识库中只保存稳定的英文标识，中文显示文字保存在代码的常量映射表中，**不随每条记录重复保存**。

实体类型和关系类型都遵循这条规则：

```text
知识库中的数据                        代码中的常量表
"type": "formula"   →   EntityType    formula  → 公式
"type": "derives"   →   RelationType  derives  → 推导出
```

这样同一段中文只维护一份，也不会出现「同一种关系在不同记录里写成不同中文」的情况。

同理，数据里也不保存可以由其他字段推导出来的值（例如关系是否有向，由 `type` 决定，见 8.1）。

### 2.3 公式作为独立知识实体

公式需要被搜索、点击、关联和单独展示，因此公式不是普通字符串，而是 `KnowledgeEntity` 的一种类型。

### 2.4 查询结果不写入固定知识库

搜索结果、邻居结果、路径结果和 AI 检索上下文由后端运行时生成，不保存在知识库文件中。

### 2.5 AI只使用图谱知识

AI 回答所需上下文来自人工编写的知识实体和关系。回答记录使用过的实体 ID，不保存教材引用。

## 4. 顶层对象：KnowledgeBase

`KnowledgeBase` 表示一个可完整加载和校验的知识库快照。

| 字段 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| `schema_version` | `string` | 是 | 数据结构版本，例如 `1.0` |
| `chapters` | `Chapter[]` | 是 | 章节列表 |
| `entities` | `KnowledgeEntity[]` | 是 | 知识实体列表 |
| `relations` | `KnowledgeRelation[]` | 是 | 知识关系列表 |

逻辑结构：

```json
{
  "schema_version": "1.0",
  "chapters": [],
  "entities": [],
  "relations": []
}
```

`schema_version` 只表示数据结构版本，不表示课程版本。

## 5. 章节对象：Chapter

`Chapter` 用于课程导航、筛选和排序，**不是知识实体**：不进 `EntityType` 枚举、不参与知识关系、不进入知识图谱、不参与实体搜索。

章节与实体的分工：

| | 章节 | 知识实体 |
| --- | --- | --- |
| 关系 | 只有包含，由 `parent_id` 表达 | 有 9 种语义关系，见第 8 节 |
| 归属 | 被实体引用 | 用 `chapter_id` 指向章节，只能有一个 |
| 搜索 | 只按名称做导航 | 全字段搜索 |
| 图谱 | 不出现 | 节点 |

| 字段 | 类型 | 必填 | 约束与说明 |
| --- | --- | --- | --- |
| `id` | `string` | 是 | 章节列表中唯一，使用英文 kebab-case |
| `name` | `string` | 是 | 章节中文名称 |
| `order` | `integer` | 是 | 大于等于 1，**全局不重复**，用于排序 |
| `parent_id` | `string \| null` | 是 | 当前阶段一律为 `null`，见 5.1 |
| `description` | `string` | 是 | 章节简介，可以为空字符串 |

示例：

```json
{
  "id": "time-varying-field",
  "name": "时变电磁场",
  "order": 5,
  "parent_id": null,
  "description": "研究随时间变化的电场、磁场及其相互作用。"
}
```

### 5.1 当前阶段采用平铺结构

`parent_id` 字段保留，但第一版所有章节一律写 `null`，不使用层级。

理由：MVP 先覆盖 6 个一级章节，平铺已经够用；不用层级可以省掉递归渲染和「父子循环」两条校验。

字段保留是为了后续扩展。将来要加层级时，只需：给部分章节补上 `parent_id` 的值 → 把第 16 节第 19 条替换为「父章节必须存在」和「不能形成父子循环」→ 前端改为递归渲染。**数据结构和已有数据都不用改。**

### 5.2 章节 ID 与实体 ID 的命名空间

章节 ID 和实体 ID 各自在自己的列表中唯一，**两者不共享命名空间**，因此允许出现两个列表里存在同一个字符串。程序通过字段区分引用：实体归属章节看 `chapter_id`，知识关系看 `source_id` / `target_id`。

章节名称与实体名称允许相同，因为二者承担不同职责：章节负责课程导航和范围说明，概念实体负责定义、搜索、图谱关系和 AI 检索上下文。若章节名本身也是有教学价值的概念（例如「静电场」），应正常建立同名的 `concept` 实体，不能用 `Chapter.description` 代替。

同名时应保持内容分工：`Chapter.description` 说明本章研究范围，概念实体的 `summary` 和 `details` 说明正式定义与核心性质。ID 优先使用自然语义区分，例如章节使用 `electrostatics`、概念使用 `electrostatic-field`；不强制添加 `-chapter` 或 `-concept` 后缀。若两者 ID 确实相同，仍可依靠所在列表和引用字段区分。前端同时展示二者时，应明确标注「章节」或「概念」。

## 6. 知识实体：KnowledgeEntity

`KnowledgeEntity` 表示可以被搜索、点击、展示和建立关系的知识对象。

### 6.1 公共字段

所有实体类型共享以下字段。

| 字段 | 类型 | 必填 | 约束与说明 |
| --- | --- | --- | --- |
| `id` | `string` | 是 | 全局唯一，使用英文 kebab-case |
| `name` | `string` | 是 | 中文标准名称 |
| `type` | `EntityType` | 是 | 固定实体类型枚举 |
| `summary` | `string` | 是 | 简明知识说明，用于卡片和搜索结果 |
| `chapter_id` | `string` | 是 | 所属章节，**只能有一个**，必须引用已存在的章节 |
| `aliases` | `string[]` | 是 | 别名列表，没有别名时为空数组 |
| `tags` | `string[]` | 是 | 用于搜索和筛选的标签 |
| `conditions` | `string[]` | 是 | 适用条件，没有条件时为空数组 |
| `details` | `object` | 是 | 根据实体类型使用对应详情结构 |

两点说明：

- **`conditions` 属于公共字段**，不再分散在各 `details` 结构中。公式的成立条件、方法的适用范围、定律的有效条件都写在这里，前端详情面板只需渲染一次，不必判断类型。
- **一个实体只属于一个章节。** 跨章节的关联用知识关系表达（例如 `related_to`），不使用多章节归属。

基础示例：

```json
{
  "id": "electric-dipole",
  "name": "电偶极子",
  "type": "concept",
  "summary": "由两个等量异号点电荷组成的电荷系统。",
  "chapter_id": "electrostatic-field",
  "aliases": ["偶极子"],
  "tags": ["电荷", "静电场"],
  "conditions": [],
  "details": {
    "definition": "两个相距很近的等量异号点电荷组成的系统。",
    "key_points": ["远场近似下由电偶极矩描述", "电场分布具有轴对称性"],
    "common_misconceptions": []
  }
}
```

### 6.2 EntityType枚举

| 枚举值 | 中文含义 | 示例 |
| --- | --- | --- |
| `concept` | 概念 | 静电场、电磁波、极化 |
| `quantity` | 物理量 | 电场强度、磁感应强度 |
| `law` | 定律或定理 | 高斯定律、法拉第定律 |
| `formula` | 公式或方程 | 波动方程、连续性方程 |
| `method` | 分析方法 | 镜像法、分离变量法 |
| `application` | 工程应用 | 传输线、波导、天线 |

实体类型在数据中只能使用上表中的英文枚举值。中文名称由前端映射显示。

与 v0.1 的差异：

- **不设 `chapter`。** 章节是独立对象，不是实体，见第 5 节。
- **不设 `phenomenon`。** 物理现象（电磁感应、极化等）用 `concept` 表达，「发生条件」写在公共字段 `conditions` 中。若后续确需按现象筛选，在枚举中恢复 `phenomenon` 并复用 `ConceptDetails` 即可，代价极小。
- **`law` 不单独定义详情结构。** 定律复用 `ConceptDetails`，见 7.1。

## 7. 各类实体的details结构

`details` **只保存该实体类型独有的结构化字段**。可以通用的内容一律放在公共字段中：

- 卡片摘要、搜索结果用 `summary`；
- 适用条件、成立条件、发生条件统一用 `conditions`（见 6.1）。

因此 6 种实体类型只需要 **5 种** `details` 结构，`law` 复用 `concept`：

| `type` | `details` 结构 |
| --- | --- |
| `concept` | ConceptDetails |
| `law` | ConceptDetails |
| `quantity` | QuantityDetails |
| `formula` | FormulaDetails |
| `method` | MethodDetails |
| `application` | ApplicationDetails |

### 7.1 ConceptDetails

适用于 `type = "concept"` 和 `type = "law"`。

| 字段 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| `definition` | `string` | 是 | 概念的正式定义；`law` 类型下为定律的文字表述 |
| `key_points` | `string[]` | 是 | 核心要点；`law` 类型下为物理意义 |
| `common_misconceptions` | `string[]` | 是 | 常见误解，没有时为空数组 |

`law` 类型示例（注意 `conditions` 在实体层级，不在 `details` 里）：

```json
{
  "id": "gauss-law",
  "name": "高斯定律",
  "type": "law",
  "summary": "通过任意闭合曲面的电通量只由该曲面内的电荷决定。",
  "chapter_id": "electrostatic-field",
  "aliases": ["高斯定理"],
  "tags": ["电通量", "闭合曲面"],
  "conditions": ["适用于静电场"],
  "details": {
    "definition": "通过任意闭合曲面的电通量等于该曲面所包围的电荷量除以真空介电常数。",
    "key_points": ["电通量只与曲面内的电荷有关", "是麦克斯韦方程组的基本方程之一"],
    "common_misconceptions": ["曲面外的电荷对电通量没有贡献，但仍会影响曲面上各点的场强"]
  }
}
```

### 7.2 QuantityDetails

适用于 `type = "quantity"`。

| 字段 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| `symbol` | `string` | 是 | 常用符号，例如 `E` |
| `unit` | `string \| null` | 是 | SI 单位；无量纲时使用 `null` |
| `dimension` | `string \| null` | 是 | 量纲，不使用时为 `null` |
| `value_kind` | `scalar \| vector` | 是 | 标量或矢量 |

物理量的文字定义写在公共字段 `summary` 中，此处不重复保存。

示例：

```json
{
  "symbol": "E",
  "unit": "V/m",
  "dimension": null,
  "value_kind": "vector"
}
```

### 7.3 FormulaDetails

适用于 `type = "formula"`。

| 字段 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| `latex` | `string` | 是 | 用于前端数学渲染的 LaTeX，不能为空 |
| `plain_text` | `string` | 是 | 便于搜索和调试的纯文本形式 |
| `variables` | `FormulaVariable[]` | 是 | 公式变量列表，没有变量时为空数组 |

公式的成立条件写在公共字段 `conditions` 中。

公式与定律的关联**不使用字段保存**，改用 `expresses` 关系表达（见 8.1）。这样同一件事只有一处记录。

公式实体示例：

```json
{
  "id": "faraday-law-differential-form",
  "name": "法拉第定律微分形式",
  "type": "formula",
  "summary": "描述时变磁场产生旋涡电场。",
  "chapter_id": "time-varying-field",
  "aliases": ["法拉第方程"],
  "tags": ["旋度", "电磁感应"],
  "conditions": ["适用于时变电磁场", "介质连续"],
  "details": {
    "latex": "\\nabla \\times \\mathbf{E} = -\\frac{\\partial \\mathbf{B}}{\\partial t}",
    "plain_text": "∇ × E = −∂B/∂t",
    "variables": [
      {
        "symbol": "E",
        "name": "电场强度",
        "quantity_id": "electric-field-intensity",
        "unit": "V/m",
        "description": "空间中的电场强度矢量。"
      },
      {
        "symbol": "B",
        "name": "磁感应强度",
        "quantity_id": "magnetic-flux-density",
        "unit": "T",
        "description": "空间中的磁感应强度矢量。"
      }
    ]
  }
}
```

### 7.4 FormulaVariable

`FormulaVariable` 嵌套在 `FormulaDetails.variables` 中，不作为顶层对象保存。

| 字段 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| `symbol` | `string` | 是 | 变量符号 |
| `name` | `string` | 是 | 中文名称 |
| `quantity_id` | `string \| null` | 是 | 对应物理量实体；没有时为 `null` |
| `unit` | `string \| null` | 是 | 单位；无单位时为 `null` |
| `description` | `string` | 是 | **在该公式中**的含义 |

`quantity_id` 有两个作用：一是前端展示公式时点击变量能跳转到对应物理量；二是加载时校验 `name` 和 `unit` 是否与物理量一致，防止同一个物理量在不同公式里写法不一致（见第 16 节第 14 条）。

### 7.5 MethodDetails

适用于 `type = "method"`。

| 字段 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| `purpose` | `string` | 是 | 方法用途 |
| `steps` | `string[]` | 是 | 主要步骤 |

方法的适用范围写在公共字段 `conditions` 中。

### 7.6 ApplicationDetails

适用于 `type = "application"`。

| 字段 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| `scenario` | `string` | 是 | 应用场景 |
| `key_parameters` | `string[]` | 是 | 关键参数或关注点 |

应用的文字说明写在公共字段 `summary` 中，此处不重复保存。

## 8. 知识关系：KnowledgeRelation

`KnowledgeRelation` 表示两个知识实体之间的语义关系。

| 字段 | 类型 | 必填 | 约束与说明 |
| --- | --- | --- | --- |
| `source_id` | `string` | 是 | 起点实体 ID，必须存在 |
| `target_id` | `string` | 是 | 终点实体 ID，必须存在 |
| `type` | `RelationType` | 是 | 固定关系类型枚举，**同时决定方向和显示名称** |
| `description` | `string` | 是 | 对这条关系的完整说明，不能为空 |

只有 4 个字段。下面三个字段是**故意不设**的：

| 不设的字段 | 原因 |
| --- | --- |
| ~~`id`~~ | 没有任何对象引用关系。前端列表用 `source_id + target_id` 做 key 即可，唯一性改由「三元组不重复」校验保证（第 16 节第 4 条） |
| ~~`label`~~ | 中文名称由 `type` 唯一决定，放在常量映射表里，见 2.2 |
| ~~`directed`~~ | 是否有向由 `type` 唯一决定，见 8.1。存成字段会允许写出「`derives` 但无向」这种自相矛盾的数据，而两个字段都填了值就无法校验 |

示例：

```json
{
  "source_id": "maxwell-equations",
  "target_id": "wave-equation",
  "type": "derives",
  "description": "在均匀、线性、无源介质中，麦克斯韦方程组可以推导出波动方程。"
}
```

`description` 必填且不能为空，理由有两个：

- 前端展示相邻知识时，学生看到的不应只是「推导出」三个字，而是为什么推导得出来；
- AI 问答会把关系说明一起送进模型（见第 18 节），带说明的检索上下文质量明显更高。

### 8.1 RelationType枚举

| 枚举值 | 中文含义 | 方向（强制） | 本课程示例 |
| --- | --- | --- | --- |
| `prerequisite` | 前置知识 | 前置 → 后续 | 矢量分析 → 静电场 |
| `defines` | 定义 | 定义者 → 被定义对象 | 电场强度定义式 → 电场强度 |
| `expresses` | 表达为 | 定律或概念 → 公式 | 高斯定律 → 高斯定律积分形式 |
| `derives` | 推导出 | 已知知识 → 推导结果 | 麦克斯韦方程组 → 波动方程 |
| `uses` | 使用 | 使用者 → 被使用对象 | 镜像法 → 唯一性定理 |
| `describes` | 描述 | 定律或公式 → 现象或概念 | 法拉第定律 → 电磁感应 |
| `applies_to` | 应用于 | 方法或知识 → 应用对象 | 镜像法 → 接地导体球问题 |
| `equivalent_to` | 等价于 | **无向** | 法拉第定律微分形式 ↔ 积分形式 |
| `related_to` | 相关 | **无向**，兜底 | 电磁波 ↔ 平面波 |

方向是**强制**的，不是建议。因为 `directed` 字段已经删除，方向完全由 `type` 决定，数据里写不出「有向关系却被标成无向」这种矛盾。

但要注意：**起点和终点写反了是校验不出来的**。程序不知道到底是「A 推导出 B」还是「B 推导出 A」，这属于语义。写数据时必须自己确认方向，写反了不会报错，只会让路径查询和相邻知识展示静默地给出错误结果。

### 8.2 两种无向关系容易变成垃圾场

`equivalent_to` 和 `related_to` 是仅有的两种无向关系，要控制使用：

- **`equivalent_to`** 只用于两个实体在物理上完全等价的情形，例如积分形式与微分形式。不要用来表示「差不多」。
- **`related_to`** 只在确实有联系、但一时说不清属于哪一种具体关系时使用。写之前先问「这是前置、推导、使用还是应用」，四种都排除之后再用它。

### 8.3 已有字段的关联不要再建关系

下面两件事已经有专用字段，**不允许**再用关系表达一遍：

| 事实 | 用什么表达 | 不要用 |
| --- | --- | --- |
| 实体属于哪个章节 | 实体的 `chapter_id` 字段 | `contains` 关系 |
| 公式里出现哪个物理量 | `FormulaVariable.quantity_id` 字段 | `uses` 关系 |

同一个事实存两份，迟早会不一致。`uses` 留给「方法使用某个定理或概念」这类没有对应字段的场景。

### 8.4 `prerequisite` 与 `derives` 不自动推导

「A 推导出 B」在逻辑上隐含「A 是 B 的前置知识」，但系统**不会自动补一条 `prerequisite`**。

需要时把两条都显式写出来。因为学习路径和推导链是学生想看的两种不同视角：问「学波动方程前要会什么」应该被明确告知「麦克斯韦方程组」，而不是让程序去猜。

### 8.5 v0.1 的 `contains` 已删除

v0.1 有 10 种关系类型，其中 `contains`（包含）已删除，因为它的用法全部被别的东西覆盖了：

| `contains` 原本想表达 | 现在用什么 |
| --- | --- |
| 章节包含知识点 | `chapter_id` 字段 |
| 麦克斯韦方程组包含法拉第定律微分形式 | `expresses`（定律 → 公式） |
| 电磁波包含平面波 | `related_to` |

保留一个自己没有清晰用法的类型，只会让编写数据时反复犹豫该选哪个。

## 9. 搜索对象

### 9.1 SearchQuery

| 字段 | 类型 | 必填 | 默认值 | 说明 |
| --- | --- | --- | --- | --- |
| `keyword` | `string` | 否 | `""` | 搜索文字，去除首尾空格。**为空表示不限定关键词** |
| `entity_types` | `EntityType[]` | 否 | `[]` | 空数组表示不过滤类型 |
| `chapter_ids` | `string[]` | 否 | `[]` | 空数组表示不过滤章节 |
| `limit` | `integer` | 否 | `50` | 范围 1～200 |

`keyword` 允许为空，是为了支持 PRD §5.1 的「按知识类型筛选」：不输关键词、只选类型，就是浏览该类型下的全部知识点。

第一版实体总数不超过 200，不做分页。如果结果被 `limit` 截断，前端应提示「只显示前 N 条」。

### 9.2 SearchResult

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `entity` | `KnowledgeEntity` | 匹配的知识实体 |
| `score` | `number` | 匹配分数，范围 0～1 |
| `matched_fields` | `string[]` | 命中的字段，取值：`name` / `aliases` / `tags` / `plain_text` / `summary` |

搜索接口**固定返回 `SearchResult[]`**，不提供「第一版先返回 `KnowledgeEntity[]`」的过渡方案。

理由：`matched_fields` 是前端高亮命中位置的依据，`score` 是排序依据，两者都是界面真正需要的信息。先返回裸实体、以后再加一层包装，对前端是破坏性改动，而一开始就返回完整结构只多几行代码。

### 9.3 搜索字段与评分

搜索字段和权重固定如下，取所有命中字段中的**最高分**作为 `score`：

| 命中字段 | 权重 | 说明 |
| --- | --- | --- |
| `name` 完全相等 | 1.0 | 输入「高斯定律」精确命中 |
| `name` 部分匹配 | 0.8 | 输入「高斯」命中 |
| `aliases` | 0.6 | 输入「高斯定理」命中别名 |
| `tags` | 0.4 | |
| `plain_text` | 0.3 | 仅公式实体有，用于搜 `∇×E` 这类表达式 |
| `summary` | 0.2 | |

排序规则：`score` 降序；`score` 相同时按 `EntityType` 枚举顺序、再按 `id` 升序排列，保证结果不随数据文件的顺序变化。

**不搜 `chapter`**（章节是独立导航对象），也不搜 `details` 里的数组内容。第一版不用模糊匹配和向量检索（见第 18 节）。

## 10. 邻居查询对象

### 10.1 NeighborQuery

| 字段 | 类型 | 必填 | 默认值 | 说明 |
| --- | --- | --- | --- | --- |
| `entity_id` | `string` | 是 | 无 | 中心实体 ID |
| `direction` | `incoming \| outgoing \| both` | 否 | `both` | 查询方向 |
| `relation_types` | `RelationType[]` | 否 | `[]` | 空数组表示不过滤关系类型 |

默认 `both`，和 `PathQuery` 默认 `directed` 不一样，这是有意为之：

- **邻居查询是「查」，两个方向的信息都有用。** 详情页要说清「前置知识有哪些」和「后续知识有哪些」，只看一个方向就不完整。方向信息放在每条结果的 `direction` 字段上。
- **路径查询是「走」，方向决定意义。** 顺着关系方向走得到的才是学习路径，反着走没有意义。

### 10.2 NeighborItem

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `entity` | `KnowledgeEntity` | 相邻的知识实体 |
| `relation` | `KnowledgeRelation` | 连接中心实体的关系 |
| `direction` | `incoming \| outgoing \| undirected` | 相对于中心实体的方向 |

`direction` 比 v0.1 多了一个 `undirected`：`equivalent_to` 和 `related_to` 是无向关系，用 `incoming` 或 `outgoing` 都描述不了。

无向关系在结果中只出现**一次**，`direction` 记为 `undirected`，不要拆成 incoming 和 outgoing 两条重复返回。

### 10.3 NeighborResult

```text
NeighborResult
├── center_id: string
└── items: NeighborItem[]
```

## 11. 路径查询对象

### 11.1 PathQuery

| 字段 | 类型 | 必填 | 默认值 | 说明 |
| --- | --- | --- | --- | --- |
| `start_id` | `string` | 是 | 无 | 起点实体 ID |
| `end_id` | `string` | 是 | 无 | 终点实体 ID |
| `direction` | `directed \| undirected` | 否 | `directed` | 路径搜索方式，默认顺着关系方向 |
| `allowed_relation_types` | `RelationType[]` | 否 | `[]` | 允许经过的关系类型 |
| `max_depth` | `integer` | 否 | `6` | 最大路径深度 |

**`direction` 默认 `directed`**，即只顺着关系方向走。因为关系方向是强制的（见 8.1），顺着方向走得到的才是真正的学习路径：从「矢量分析」出发能走到「电磁波」，反过来走不通。

要反查「哪些知识指向它」时，显式传 `undirected`。注意无向搜索会让「电磁波 → 矢量分析」也变成可达，语义上不是学习路径，只适合做关联探索。

### 11.2 PathResult

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `found` | `boolean` | 是否找到路径 |
| `entities` | `KnowledgeEntity[]` | 按路径顺序排列的实体 |
| `relations` | `KnowledgeRelation[]` | 按路径顺序排列的关系 |
| `message` | `string \| null` | 无路径或错误说明 |

字段名从 v0.1 的 `nodes` 改为 `entities`，与 `GraphView.entities` 、`KnowledgeBase.entities` 保持一致。`nodes` 是图论术语，不应该出现在对外接口里。

当 `found = true` 时必须满足：

```text
relations.length = entities.length - 1
```

采用 `directed` 搜索时，第 i 条关系必须与路径前进方向一致：

```text
relations[i].source_id = entities[i].id
relations[i].target_id = entities[i + 1].id
```

采用 `undirected` 搜索时，实际方向可能与路径顺序相反，上式不成立；返回时**不翻转关系对象**，由前端根据两端的位置自行判断箭头方向。

`start_id` 与 `end_id` 相同时，返回 `found = true`、`entities` 只包含该实体、`relations` 为空数组。

## 12. 局部图谱对象

### 12.1 GraphQuery

| 字段 | 类型 | 必填 | 默认值 | 说明 |
| --- | --- | --- | --- | --- |
| `center_id` | `string \| null` | 否 | `null` | 中心实体；为 `null` 时返回全局图谱 |
| `depth` | `integer` | 否 | `1` | 从中心向外展开的层数，范围 1～3 |
| `entity_types` | `EntityType[]` | 否 | `[]` | 空数组表示不过滤类型 |
| `relation_types` | `RelationType[]` | 否 | `[]` | 空数组表示不过滤关系类型 |

三条取值规则：

1. `center_id` 为 `null` 时，`depth` **被忽略**（全局图谱不分层），不报错。
2. `center_id` 不存在时返回 404，**不静默退化为返回全图**。
3. `entity_types` 过滤**不作用于中心实体**：即使中心的类型不在过滤列表里，它也必须出现在结果中，否则图谱就没有中心可画了。

`depth` 上限为 3：本课程实体不到 200 个，3 层已经基本等于全图；不设上限会让一个请求把整个图谱拉出来。

### 12.2 GraphView

```text
GraphView
├── center_id: string | null
├── entities: KnowledgeEntity[]
└── relations: KnowledgeRelation[]
```

**返回的 `relations` 中，每条关系的 `source_id` 和 `target_id` 必须都能在 `entities` 里找到。**

过滤掉某个实体后，连着它的关系必须一起丢掉。不能留下悬空边：前端图库遇到指向不存在节点的边会直接报错，或者画出断线。

## 13. AI问答对象

### 13.1 AIQuestionRequest

| 字段 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| `question` | `string` | 是 | 当前用户问题，去除首尾空格后不能为空，长度不超过 500 字 |
| `context_entity_id` | `string \| null` | 否 | 用户当前正在查看的知识实体 |
| `history` | `AIConversationTurn[]` | 否 | 最近的完整问答轮次，默认 `[]`，最多 10 项，按时间从旧到新排列 |

示例：

```json
{
  "question": "它在什么条件下适用？",
  "context_entity_id": null,
  "history": [
    {
      "question": "介绍一下高斯定律。",
      "answer": "高斯定律描述通过闭合曲面的电通量与其内部电荷之间的关系。",
      "used_entity_ids": ["gauss-law"]
    }
  ]
}
```

### 13.2 AIConversationTurn

`AIConversationTurn` 表示一个已经完成的问答轮次，只随下一次请求由前端传回，不写入知识库或服务端存储。

| 字段 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| `question` | `string` | 是 | 该轮用户问题，长度不超过 500 字 |
| `answer` | `string` | 是 | 该轮 AI 回答，长度不超过 4000 字 |
| `used_entity_ids` | `string[]` | 是 | 该轮回答使用的实体 ID，没有时为 `[]` |

一轮是一个完整的「用户问题 + AI 回答」。前端每次发送当前问题时，只携带最近 10 轮；超过 10 轮时从最早一轮开始丢弃。后端同样校验 `history` 最多 10 项，不接受由客户端无限扩大的上下文。

`used_entity_ids` 帮助后端理解“它”“这个公式”等省略了主语的追问，但历史回答本身不是知识依据。每一轮仍必须重新检索知识图谱，并且只能根据当前检索得到的实体和关系回答。

### 13.3 RetrievalContext

`RetrievalContext` 是后端内部对象，不直接写入知识库。

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `question` | `string` | 当前原始问题 |
| `history` | `AIConversationTurn[]` | 当前请求携带的最近问答上下文 |
| `matched_entity_ids` | `string[]` | 当前问题结合上下文后匹配到的知识实体 |
| `entities` | `KnowledgeEntity[]` | 提供给 AI 的知识实体 |
| `relations` | `KnowledgeRelation[]` | 提供给 AI 的知识关系 |
| `retrieval_message` | `string \| null` | 检索不足等说明 |

`matched_entity_ids` 和 `entities` 不是同一件事，两个都要保留：

- `matched_entity_ids`：检索阶段**直接命中**的实体；
- `entities`：**真正送给模型的**实体，等于直接命中的实体再加上通过关系扩充进来的邻居。

`relations` 同理，是扩充过程中一并带上的关系，用于给模型提供推导依据。`history` 只用于理解当前问题的上下文，不替代图谱证据。

### 13.4 AIAnswerResponse

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `answer` | `string` | AI生成的回答 |
| `used_entity_ids` | `string[]` | 回答使用过的知识实体 |
| `insufficient_knowledge` | `boolean` | 当前图谱是否缺少足够知识 |
| `message` | `string \| null` | 补充说明或错误提示 |

`insufficient_knowledge` 由**后端**判定，不由模型自己声明：

- 检索阶段一个实体都没命中 → 后端直接把 `insufficient_knowledge` 置为 `true`，返回固定话术，**不调用模型**；
- 有命中，但模型回答里用到的实体为空 → 同样置为 `true`。

这样 PRD 第 10 条验收标准（「AI 无法从知识库确认时能明确说明信息不足」）就变成一条可测的规则，而不是指望模型自觉。

`used_entity_ids` 里的每个 ID 都必须能在知识库中找到（第 16 节第 8 条）。模型返回了不存在的 ID 时，后端应剔除并在 `message` 里说明，不能把错误 ID 透传给前端。

只返回 ID、不返回实体对象：前端打开图谱页时已经拿到全量实体，用 ID 在本地查即可，不必为回答里的每个知识点再发一次请求。

AI 接口失败时（模型超时、未配置密钥等）返回明确的 `message`，**不影响**搜索、图谱、路径等其他接口——这是 PRD 第 11 条验收标准。

示例：

```json
{
  "answer": "在均匀、线性、无源介质中，可以对麦克斯韦旋度方程再次取旋度，并结合物质关系消去磁场量，从而得到电场波动方程。",
  "used_entity_ids": [
    "maxwell-equations",
    "material-relations",
    "wave-equation"
  ],
  "insufficient_knowledge": false,
  "message": null
}
```

第一版不保存由大模型自行给出的数值置信度，因为该数值通常不能可靠代表答案正确率。

### 13.5 多轮上下文与问答历史

MVP 支持当前标签页内的连续多轮问答，但服务端不持久化用户问答历史。后端不维护 `conversation_id`，也不把问题和回答写入 JSON、数据库或日志型业务存储。`AIQuestionRequest` 和 `AIAnswerResponse` 仍按请求产生和返回。

前端使用当前标签页的 `sessionStorage` 缓存最近 10 个完整轮次，并通过 `AIQuestionRequest.history` 随请求携带。刷新页面后恢复，关闭标签页后自动清除。若后续需要跨标签页或跨设备历史，再单独设计用户身份、会话和消息存储，不扩充当前知识库文件。

## 15. ID命名规范

### 15.1 通用规则

- 只使用小写英文字母、数字和连字符；
- 不使用空格、中文和下划线；
- ID 创建后不因显示名称变化而修改；
- 实体 ID 在整个知识库中唯一；
- 章节 ID 在章节列表中唯一。

关系没有 ID 字段，见第 8 节。

### 15.2 示例

```text
章节：time-varying-field
实体：maxwell-equations
实体：electric-field-intensity
公式：faraday-law-differential-form
```

## 16. 数据校验规则

知识库加载时必须完成以下校验。校验不通过应直接报错并指出具体位置，不能带着错误数据启动服务。

**结构与标识**

1. `schema_version` 必须是系统支持的版本。
2. 所有章节 ID 必须唯一。
3. 所有实体 ID 必须唯一。
4. 关系的 `source_id + target_id + type` 三元组不允许重复。

**引用完整性**

5. 每个实体的 `chapter_id` 必须存在。
6. 关系的 `source_id` 和 `target_id` 必须存在。
7. `FormulaVariable.quantity_id` 必须为 `null` 或指向 `type = "quantity"` 的实体。
8. `AIAnswerResponse.used_entity_ids` 和 `AIConversationTurn.used_entity_ids` 必须全部存在于知识库中。

**类型与结构匹配**

9. 实体的 `type` 必须属于 `EntityType`。
10. **`details` 结构必须与 `type` 匹配**（对照表见第 7 节）。这是最容易写错数据的地方，必须校验，否则错误数据会在前端渲染时才暴露。
11. 关系的 `type` 必须属于 `RelationType`。
12. `QuantityDetails.value_kind` 必须是 `scalar` 或 `vector`。
13. `FormulaDetails.latex` 去除首尾空格后不能为空。

**取值与一致性**

14. `FormulaVariable` 填写了 `quantity_id` 时，它的 `name` 和 `unit` 必须与目标物理量的 `name` 和 `unit` 一致。
15. 关系不允许起点和终点相同（`source_id != target_id`）。
16. 数组字段没有内容时使用 `[]`，不能省略或写成 `null`。
17. 所有用户可见名称和说明去除首尾空格后不能为空。
18. 章节的 `order` 必须大于等于 1 且不重复。
19. `AIQuestionRequest.history` 最多包含 10 个完整轮次；其中每个 `question` 不超过 500 字，每个 `answer` 不超过 4000 字。

**当前阶段专属**

20. 所有章节的 `parent_id` 必须为 `null`。将来启用层级后，此条替换为「父章节必须存在」和「章节之间不能形成父子循环」两条。

## 17. 知识库文件与加载方式

MVP 和正式版均直接维护一个完整知识库文件：

```text
knowledge_data/
└── knowledge_base.json
```

`knowledge_base.json` 是知识库的唯一数据源，包含 `chapters`、`entities` 和 `relations`。文件进入 Git 管理，内容修改通过提交记录审查和回滚。

运行流程：

```text
人工编辑 knowledge_base.json
          ↓
FastAPI 启动时执行完整校验
          ↓
一次性加载到内存并建立查询索引
          ↓
前端通过 API 查询
```

后端至少建立以下只读索引：

- `entity_by_id`：实体 ID 到实体的映射；
- `chapter_by_id`：章节 ID 到章节的映射；
- `outgoing_relations`：按 `source_id` 分组的关系；
- `incoming_relations`：按 `target_id` 分组的关系。

每个请求复用同一份内存数据和索引，不重新读取 JSON，也不复制完整知识库。AI 问答只传递检索到的局部实体和关系，不把整个知识库发送给模型。

当前不增加按章节拆分、合并生成、SQLite、PostgreSQL或向量数据库，知识库先使用单个 JSON 文件。后续存储路线确定为迁移到 Neo4j；迁移时保持 `KnowledgeEntity`、`KnowledgeRelation` 和对外查询接口不变，主要替换存储访问层。

## 18. RAG检索数据流

```text
AIQuestionRequest（当前问题 + 最近 10 轮 history）
        ↓
结合 history.used_entity_ids 理解省略主语，再按第 9.3 节的字段权重匹配
        ↓
邻居查询或路径查询扩充上下文
        ↓
RetrievalContext
        ↓
若一个实体都没命中：直接返回 insufficient_knowledge = true，不调模型
        ↓
大模型生成结构化回答
        ↓
后端校验 used_entity_ids
        ↓
AIAnswerResponse
```

第一版不要求向量数据库。后续只有在实体数量和自然语言表达复杂度明显增加时，才评估增加向量语义检索。

## 19. 设计决定汇总

### 19.1 v0.2 已确定

- 章节作为独立对象，不作为知识实体，`EntityType` 中不设 `chapter`；
- 章节采用平铺结构，`parent_id` 一律为 `null`；
- 章节 ID 与实体 ID 各自唯一，不加后缀区分；
- `EntityType` 共 6 类，不设 `phenomenon`；
- `details` 使用严格的分类型结构，共 5 种，`law` 复用 `ConceptDetails`；
- `conditions` 作为公共字段，不放在 `details` 中；
- 一个知识实体只属于一个章节；
- MVP 先覆盖 6 个章节：矢量分析、静电场、恒定电流场、恒定磁场、时变电磁场、电磁波；
- MVP 阶段使用单个 `knowledge_data/knowledge_base.json`，启动时一次性校验并加载到内存；
- 后续存储方案确定迁移到 Neo4j，对外数据结构和接口保持不变；
- 章节与概念允许同名；同名概念仍建立实体，二者通过职责、引用字段和界面标识区分；
- MVP 不持久化用户问答历史；
- AI 支持当前页面内连续多轮问答，前端每次携带最近 10 个完整问答轮次，后端无状态；
- `RelationType` 共 9 类，删除 `contains`；
- 关系只保存 `source_id` / `target_id` / `type` / `description` 四个字段，不设 `id` / `label` / `directed`；
- 关系方向强制，与 `type` 一一对应；
- 公式与物理量的关联只用 `FormulaVariable.quantity_id`，不建关系；
- 路径查询默认 `directed`，邻居查询默认 `both`；
- 搜索固定返回 `SearchResult[]`，`keyword` 允许为空；
- 查询对象统一命名为 `XxxQuery` / `XxxResult`（除 AI 问答）。
