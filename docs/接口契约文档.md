## 0. 本文档的定位

三份文档的分工：

```text
产品需求文档.md        要做什么（页面、功能、验收标准）
数据结构设计文档.md    数据长什么样（对象、字段、校验规则）
接口契约文档.md         ← 本文档：前后端之间怎么说话（URL、参数、响应、错误）
```

本文档是前端和后端的**共同依据**。改接口必须先改本文档。文档里的字段名与《数据结构设计文档.md》保持一致，不另起一套命名。

## 1. 通用约定

### 1.1 基础信息

| 项 | 约定 |
| --- | --- |
| 基础路径 | `/api` |
| 本地地址 | `http://127.0.0.1:8000` |
| 编码 | 请求与响应统一使用 UTF-8 |
| 数据格式 | 请求体和响应体均为 JSON |
| 鉴权 | **无**。第一版是本地单用户工具，不登录、不区分用户 |
| 权限 | **只读**。所有接口都不会修改知识库（教师编辑功能属于 PRD 阶段五） |
| 接口文档 | FastAPI 自动生成的 `/docs` 与 `/openapi.json` 始终可用 |

### 1.2 命名规则

- 路径和参数名使用 `snake_case`，与《数据结构设计文档.md》的字段名完全一致；
- 不额外发明简称。例如搜索接口的参数就叫 `entity_types`，不叫 `types`——省一次字段名翻译，少一处出错的地方。

### 1.3 数组参数

数组类型的查询参数使用**重复参数**，不使用逗号分隔：

```text
正确：/api/entities?entity_types=law&entity_types=formula
不用：/api/entities?entity_types=law,formula
```

原因：逗号分隔需要自己写解析，而且一旦某个值本身含逗号就会解析错。重复参数由 Web 框架原生支持，不用写代码。

### 1.4 枚举值

所有枚举值（实体类型、关系类型、方向）只能使用《数据结构设计文档.md》定义的英文值。

**中文名称不由前端硬编码**，通过 `GET /api/meta` 获取。这样新增一个类型时只改后端一处，不会出现后端加了类型、前端显示不出来或显示成英文的情况。

### 1.5 响应体形状

**不套 `{code, message, data}` 外壳。** 成功时直接返回《数据结构设计文档.md》定义的对象本身：

```json
[
  { "source_id": "maxwell-equations", "target_id": "wave-equation", "type": "derives", "description": "..." }
]
```

不封装的原因：设计文档已经定义好了每个接口的返回对象，再包一层等于让每个接口多一次拆包，而且外壳里的 `code` 和 HTTP 状态码重复。错误统一用 HTTP 状态码表达，见第 2 节。

## 2. 错误约定

### 2.1 错误响应形状

所有错误**统一**为下面的形状：

```json
{
  "detail": {
    "code": "entity_not_found",
    "message": "未找到知识点：maxwell-equation",
    "field": "entity_id"
  }
}
```

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `code` | `string` | 机器可读的错误码，见 2.3，前端按它分支 |
| `message` | `string` | 给人看的说明，**必须说清原因**（PRD §8.4） |
| `field` | `string \| null` | 出错的参数名；与具体参数无关时为 `null` |

**为什么必须写自定义异常处理器：** FastAPI 默认的 404 是 `{"detail": "字符串"}`，而参数校验失败的 422 是 `{"detail": [数组]}`。同一个 `detail` 字段有两种类型，前端要写两套解析。必须注册异常处理器把**所有**错误规整成上面这一种形状，前端才能只用一条错误处理路径。

### 2.2 状态码

| 状态码 | 何时使用 |
| --- | --- |
| `200` | 成功。包括「查到了但没有结果」的情况（返回空数组，不是 404） |
| `404` | 路径里的实体 ID 不存在 |
| `422` | 查询参数格式错误或超出允许范围 |
| `502` | 调用了外部 AI 模型，模型返回失败 |
| `503` | AI 功能未配置（没有 API 密钥），此时图谱功能一切正常 |
| `500` | 其他未预期错误 |

**「没有结果」不是错误。** 搜索不到、两个知识点之间没有路径、邻居为空，都返回 `200` 加空数组或 `found: false`。只有「用户指定了一个不存在的 ID」才是 404。

### 2.3 错误码表

| `code` | HTTP | 触发场景 |
| --- | --- | --- |
| `entity_not_found` | 404 | `/api/entities/{id}` 等接口收到的实体 ID 不在知识库中 |
| `invalid_parameter` | 422 | 参数取值不在允许范围内，例如 `limit=999`、`direction=upward` |
| `ai_unavailable` | 503 | AI 接口被调用，但服务端没有配置模型密钥 |
| `ai_failed` | 502 | 模型调用超时或返回错误 |
| `internal_error` | 500 | 兜底，其他未预期异常 |

## 4. 接口详述

### 4.1 `GET /api/health`

用于前端启动时确认后端是否可用（PRD §8.3 要求图谱初次加载时有加载状态）。

**响应 `200`**

```json
{
  "status": "ok",
  "course": "电磁场与波",
  "schema_version": "1.0",
  "counts": {
    "chapters": 8,
    "entities": 23,
    "relations": 28
  }
}
```

`counts` 是给开发时看的：前端启动一次就能知道数据有没有加载全，不用打开 `/docs`。

**注意：** 如果知识库校验失败，服务根本不会启动（见第 7 节），所以这个接口只会在「数据是好的」前提下返回。

---

### 4.2 `GET /api/meta`

前端启动时调用一次，用来渲染类型图例、筛选下拉框，以及把英文枚举翻译成中文。

**响应 `200`**

```json
{
  "course": {
    "id": "electromagnetic-field-and-waves",
    "name": "电磁场与波",
    "description": "电磁场与波课程固定知识图谱。"
  },
  "schema_version": "1.0",
  "entity_types": [
    { "value": "concept", "label": "概念" },
    { "value": "quantity", "label": "物理量" },
    { "value": "law", "label": "定律或定理" },
    { "value": "formula", "label": "公式或方程" },
    { "value": "method", "label": "分析方法" },
    { "value": "application", "label": "工程应用" }
  ],
  "relation_types": [
    { "value": "prerequisite", "label": "前置知识", "directed": true },
    { "value": "defines", "label": "定义", "directed": true },
    { "value": "expresses", "label": "表达为", "directed": true },
    { "value": "derives", "label": "推导出", "directed": true },
    { "value": "uses", "label": "使用", "directed": true },
    { "value": "describes", "label": "描述", "directed": true },
    { "value": "applies_to", "label": "应用于", "directed": true },
    { "value": "equivalent_to", "label": "等价于", "directed": false },
    { "value": "related_to", "label": "相关", "directed": false }
  ]
}
```

三点说明：

1. **`entity_types` 的排列顺序是有意义的。** 搜索结果的同分排序按这个顺序做（设计文档第 9.3 节），所以这个数组是「概念 → 物理量 → 定律 → 公式 → 方法 → 应用」，不能随意调整。
2. **`directed` 在这里出现不算违反设计文档。** 设计文档说关系记录里不存 `directed`，因为它是 `type` 的函数；这里返回的是**类型表**，每个类型一份，正是那张常量表本身。
3. **课程信息放在这里，不放在知识库文件里。** `KnowledgeBase` 只有 `schema_version` / `chapters` / `entities` / `relations`，没有课程字段；课程名是一个不随数据变化的常量，放在与类型表同一个位置。

---

### 4.3 `GET /api/chapters`

返回章节列表，用于左侧章节导航和章节筛选下拉框。

**请求参数**：无。

**响应 `200`**：`Chapter[]`，**已按 `order` 升序排好**，前端不需要再排。

```json
[
  {
    "id": "vector-analysis",
    "name": "矢量分析",
    "order": 1,
    "parent_id": null,
    "description": "研究标量场与矢量场的微分运算。"
  },
  {
    "id": "electrostatic-field",
    "name": "静电场",
    "order": 2,
    "parent_id": null,
    "description": "研究静止电荷产生的电场及其与导体的相互作用。"
  }
]
```

**排序由后端负责。** 前端拿到就直接渲染，不要自己按 `order` 排——排序规则只有一处，改起来才不会漏。

章节没有详情接口。前端已经拿到完整列表，按 `id` 在本地查即可。

### 4.4 `GET /api/entities`

搜索接口，同时承担「按类型/章节浏览」的职责。对应设计文档的 `SearchQuery` → `SearchResult[]`。

**请求参数**

| 参数 | 类型 | 必填 | 默认 | 说明 |
| --- | --- | --- | --- | --- |
| `keyword` | `string` | 否 | `""` | 搜索文字。为空表示不限定关键词，只按类型和章节筛选 |
| `entity_types` | `EntityType` | 否 | 无 | 可重复。不传表示不过滤类型 |
| `chapter_ids` | `string` | 否 | 无 | 可重复。不传表示不过滤章节 |
| `limit` | `integer` | 否 | `50` | 范围 1～200 |

**请求示例**

```text
GET /api/entities?keyword=高斯
GET /api/entities?entity_types=law&entity_types=formula
GET /api/entities?chapter_ids=electrostatic-field&limit=200
GET /api/entities?keyword=E&entity_types=quantity
```

**响应 `200`**：`SearchResult[]`，已按 `score` 降序排好。

```json
[
  {
    "entity": {
      "id": "gauss-law",
      "name": "高斯定律",
      "type": "law",
      "summary": "通过任意闭合曲面的电通量只由该曲面内的电荷决定。",
      "chapter_id": "electrostatic-field",
      "aliases": ["高斯定理"],
      "tags": ["电通量", "闭合曲面"],
      "conditions": ["适用于静电场"],
      "details": {
        "definition": "通过任意闭合曲面的电通量等于该曲面所包围的电荷量除以真空介电常数。",
        "key_points": ["电通量只与曲面内的电荷有关", "是麦克斯韦方程组的基本方程之一"],
        "common_misconceptions": ["曲面外的电荷对电通量没有贡献，但仍会影响曲面上各点的场强"]
      }
    },
    "score": 1.0,
    "matched_fields": ["name"]
  }
]
```

**行为约定**

1. **搜索无结果是 `200` + `[]`**，不是 404。
2. **`chapter_ids` 传了不存在的章节返回空数组**，不报 404。筛选参数不做存在性校验——前端只会传从 `/api/chapters` 拿到的 id。
3. **匹配规则固定**，见设计文档第 9.3 节的权重表（`name` 精确 1.0 → 部分 0.8 → `aliases` 0.6 → `tags` 0.4 → `plain_text` 0.3 → `summary` 0.2）；取命中字段里的最高分。
4. **不搜章节名**、不搜 `details` 里的数组内容。
5. **`limit` 超出 1～200 返回 422**，`code` 为 `invalid_parameter`。
6. **前端默认请求 `limit=200`**（即上限）。本课程实体不超过 200 个，这样永远不会截断，界面上的数量直接就是真实的匹配总数。只有确实需要「只看前几条」时才传更小的值。

### 4.5 `GET /api/entities/{entity_id}`

知识点详情。

**路径参数**

| 参数 | 类型 | 说明 |
| --- | --- | --- |
| `entity_id` | `string` | 实体 ID |

**响应 `200`**：完整的 `KnowledgeEntity`，字段见设计文档第 6 节。

```json
{
  "id": "faraday-law-differential-form",
  "name": "法拉第定律微分形式",
  "type": "formula",
  "summary": "描述时变磁场产生旋涡电场。",
  "chapter_id": "time-varying-field",
  "aliases": ["法拉第方程"],
  "tags": ["旋度", "电磁感应"],
  "conditions": ["适用于时变电磁场", "介质连续"],
  "details": {
    "latex": "\\nabla \\times \\mathbf{E} = -\\frac{\\partial \\mathbf{B}}{\\partial t}",
    "plain_text": "∇ × E = −∂B/∂t",
    "variables": [
      {
        "symbol": "E",
        "name": "电场强度",
        "quantity_id": "electric-field-intensity",
        "unit": "V/m",
        "description": "空间中的电场强度矢量。"
      },
      {
        "symbol": "t",
        "name": "时间",
        "quantity_id": null,
        "unit": "s",
        "description": "观察时刻。"
      }
    ]
  }
}
```

**错误 `404`**

```json
{
  "detail": {
    "code": "entity_not_found",
    "message": "未找到知识点：faraday-law-differntial-form",
    "field": "entity_id"
  }
}
```

**只返回实体本身，不附带邻居。** 详情页需要邻居时再调 4.6，两个请求都是本地毫秒级。把邻居塞进详情响应会让这个接口的返回体积不可预测，也让邻居查询无法被别的页面复用。

**`details` 的结构随 `type` 变化**，前端拿到 `type` 后再决定怎么渲染。对照表在设计文档第 7 节。

### 4.6 `GET /api/entities/{entity_id}/neighbors`

查看一个知识点的一跳邻居。对应设计文档的 `NeighborQuery` → `NeighborResult`。

**路径参数**

| 参数 | 类型 | 说明 |
| --- | --- | --- |
| `entity_id` | `string` | 中心实体 ID |

**请求参数**

| 参数 | 类型 | 必填 | 默认 | 说明 |
| --- | --- | --- | --- | --- |
| `direction` | `incoming \| outgoing \| both` | 否 | `both` | 查询方向 |
| `relation_types` | `RelationType` | 否 | 无 | 可重复。不传表示不过滤关系类型 |

**请求示例**

```text
GET /api/entities/gauss-law/neighbors
GET /api/entities/gauss-law/neighbors?direction=outgoing
GET /api/entities/maxwell-equations/neighbors?relation_types=derives&relation_types=expresses
```

**响应 `200`**

```json
{
  "center_id": "gauss-law",
  "items": [
    {
      "entity": {
        "id": "electric-flux",
        "name": "电通量",
        "type": "quantity",
        "summary": "描述电场穿过某个曲面的多少的物理量。",
        "chapter_id": "electrostatic-field",
        "aliases": [],
        "tags": ["电场", "通量"],
        "conditions": [],
        "details": {
          "symbol": "Φ_E",
          "unit": "V·m",
          "dimension": null,
          "value_kind": "scalar"
        }
      },
      "relation": {
        "source_id": "gauss-law",
        "target_id": "electric-flux",
        "type": "uses",
        "description": "高斯定律用电通量描述闭合曲面上的电场分布。"
      },
      "direction": "outgoing"
    }
  ]
}
```

**行为约定**

1. **默认 `both`。** 这是和路径查询默认 `directed` 有意不同的地方，理由见设计文档第 10.1 节：邻居是「查」，两个方向都有用；路径是「走」，方向决定意义。前端详情页按 `direction` 把结果分到「前置/来源」和「后续/去向」两组。
2. **无向关系只返回一条**，`direction` 为 `undirected`。`equivalent_to` 和 `related_to` 不会同时以 incoming 和 outgoing 出现两次。
3. **中心实体不存在返回 404**，`code` 为 `entity_not_found`。
4. **没有邻居返回 `items: []`**，不是错误。
5. 中心实体**不在** `items` 里，需要的话前端自己已经有了。

### 4.7 `GET /api/path`

查询两个知识点之间的路径。对应设计文档的 `PathQuery` → `PathResult`。

**请求参数**

| 参数 | 类型 | 必填 | 默认 | 说明 |
| --- | --- | --- | --- | --- |
| `start_id` | `string` | 是 | 无 | 起点实体 ID |
| `end_id` | `string` | 是 | 无 | 终点实体 ID |
| `direction` | `directed \| undirected` | 否 | `directed` | 是否顺着关系方向查找 |
| `allowed_relation_types` | `RelationType` | 否 | 无 | 可重复。不传表示允许所有关系类型 |
| `max_depth` | `integer` | 否 | `6` | 最大路径深度，范围 1～10 |

**请求示例**

```text
GET /api/path?start_id=gradient&end_id=uniform-plane-wave
GET /api/path?start_id=maxwell-equations&end_id=wave-equation&allowed_relation_types=derives
GET /api/path?start_id=wave-equation&end_id=maxwell-equations&direction=undirected
```

**响应 `200`（找到路径）**

```json
{
  "found": true,
  "entities": [
    { "id": "maxwell-equations", "name": "麦克斯韦方程组", "type": "law", "...": "..." },
    { "id": "wave-equation", "name": "波动方程", "type": "formula", "...": "..." },
    { "id": "uniform-plane-wave", "name": "均匀平面波", "type": "application", "...": "..." }
  ],
  "relations": [
    {
      "source_id": "maxwell-equations",
      "target_id": "wave-equation",
      "type": "derives",
      "description": "在均匀、线性、无源介质中，麦克斯韦方程组可以推导出波动方程。"
    },
    {
      "source_id": "wave-equation",
      "target_id": "uniform-plane-wave",
      "type": "describes",
      "description": "波动方程描述均匀平面波在无界介质中的传播。"
    }
  ],
  "message": null
}
```

**响应 `200`（没有路径）**

```json
{
  "found": false,
  "entities": [],
  "relations": [],
  "message": "按关系方向未找到从「矢量分析」到「电偶极子」的路径，可尝试改为无向查找。"
}
```

**行为约定**

1. **默认 `directed`（顺着关系方向）。** 这样得到的才是学习路径。反查时显式传 `undirected`。
2. **无路径是 `200` + `found: false`**，不是 404。
3. **`message` 要给出下一步建议。** 有向查找失败时应该提示「可尝试无向」，而不是只说「没有路径」——PRD §8.4 要求错误信息说明原因。
4. **起点或终点不存在返回 404**，`code` 为 `entity_not_found`。
5. **不变量**：`found` 为 `true` 时必定满足 `relations.length == entities.length - 1`。
6. **`start_id == end_id`** 返回 `found: true`，`entities` 只有一个元素，`relations` 为空数组。
7. **`undirected` 时不翻转关系对象。** 路径顺序可能是 `[A, B]` 而关系是 `B → A`，这是正常的，箭头方向由前端根据两端位置判断（设计文档第 11.2 节）。
8. **返回的是最短路径**（按边数最少）。同长度时哪一条被返回不保证，这是允许的，前端不要依赖具体是哪条。

### 4.8 `GET /api/graph`

获取全局或局部知识图谱。对应设计文档的 `GraphQuery` → `GraphView`。

**请求参数**

| 参数 | 类型 | 必填 | 默认 | 说明 |
| --- | --- | --- | --- | --- |
| `center_id` | `string` | 否 | 无 | 中心实体 ID。不传表示查全图 |
| `depth` | `integer` | 否 | `1` | 从中心展开的层数，范围 1～3。`center_id` 未传时忽略 |
| `entity_types` | `EntityType` | 否 | 无 | 可重复。不传表示不过滤类型 |
| `relation_types` | `RelationType` | 否 | 无 | 可重复。不传表示不过滤关系类型 |

**请求示例**

```text
GET /api/graph
GET /api/graph?center_id=maxwell-equations&depth=2
GET /api/graph?center_id=electrostatic-field&entity_types=law&entity_types=formula
```

**响应 `200`**

```json
{
  "center_id": "maxwell-equations",
  "entities": [
    { "id": "maxwell-equations", "name": "麦克斯韦方程组", "type": "law", "...": "..." },
    { "id": "wave-equation", "name": "波动方程", "type": "formula", "...": "..." }
  ],
  "relations": [
    {
      "source_id": "maxwell-equations",
      "target_id": "wave-equation",
      "type": "derives",
      "description": "在均匀、线性、无源介质中，麦克斯韦方程组可以推导出波动方程。"
    }
  ]
}
```

**行为约定**

1. **`center_id` 不传就是全图**，`depth` 被忽略（全局图谱不分层），不报错。
2. **`center_id` 不存在返回 404**，`code` 为 `entity_not_found`。**不允许静默退化成返回全图**——那样前端会以为自己在看局部图。
3. **类型过滤不作用于中心实体。** 即使中心的类型不在 `entity_types` 里，它也必须在 `entities` 中，否则图就没有中心可画。
4. **不允许悬空边。** 返回的每条关系，其 `source_id` 和 `target_id` 都必须能在 `entities` 里找到。被过滤掉的实体，连着它的关系必须一起丢掉。**这条是硬性要求，前端图库遇到指向不存在节点的边会直接报错。**
5. `center_id` 为 `null` 时响应的 `center_id` 也是 `null`。
6. **无向关系在图中只出现一次**，不按两个方向各画一条。

### 4.9 `POST /api/ai/ask`

基于知识图谱的问答。对应设计文档的 `AIQuestionRequest` → `AIAnswerResponse`。

**请求体**

```json
{
  "question": "它的适用条件是什么？",
  "context_entity_id": null,
  "history": [
    {
      "question": "介绍一下高斯定律。",
      "answer": "高斯定律描述闭合曲面的电通量。",
      "used_entity_ids": ["gauss-law"]
    }
  ]
}
```

| 字段 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| `question` | `string` | 是 | 去空格后不能为空，最长 500 字 |
| `context_entity_id` | `string \| null` | 否 | 用户当前正在看的实体，用于补全指代 |
| `history` | `AIConversationTurn[]` | 否 | 最近的完整问答轮次，最多 10 项，按时间从旧到新排列 |

**响应 `200`**

```json
{
  "answer": "在均匀、线性、无源介质中，可以对麦克斯韦旋度方程再次取旋度，并结合物质关系消去磁场量，从而得到电场波动方程。",
  "used_entity_ids": ["maxwell-equations", "wave-equation"],
  "retrieved_entity_ids": ["maxwell-equations", "wave-equation", "faraday-law-differential-form"],
  "insufficient_knowledge": false,
  "message": null
}
```

**响应 `200`（知识不足）**

```json
{
  "answer": "当前知识库中没有足够内容回答这个问题。",
  "used_entity_ids": [],
  "retrieved_entity_ids": [],
  "insufficient_knowledge": true,
  "message": "检索没有命中任何知识点，请尝试换一种说法，或直接浏览知识图谱。"
}
```

**行为约定**

1. **`insufficient_knowledge` 由后端判定，不由模型声明。** 检索阶段一个实体都没命中时，后端直接返回上面的固定话术，**不调用模型**。这样 PRD 第 9 条验收标准就是一条可测的规则，而不是指望模型自觉。
2. **`retrieved_entity_ids` 与 `used_entity_ids` 分开统计。** 前者是检索阶段命中的知识点（交给模型的材料），后者是回答文字里**实际引用**的知识点：检索上下文里哪些知识点的名称或别名真的出现在回答中。系统提示要求模型用「」括起知识点名称，便于识别。回答里没有提到任何知识点时，`used_entity_ids` 为空、`insufficient_knowledge` 为 `true`，`message` 提示「回答没有引用任何知识点，请谨慎参考」。
3. **`used_entity_ids` 里的每个 ID 都必须在知识库中存在。** 模型返回了不存在的 ID 时，后端剔除它并在 `message` 里说明，**不能把错误 ID 透传给前端**。
4. **只返回 ID，不返回实体对象。** 前端打开图谱页时已经拿到全量实体，用 ID 在本地查即可，不必为回答里的每个知识点再发请求。
5. **AI 失败不影响其他接口。** 未配置密钥返回 `503` / `ai_unavailable`，模型调用失败返回 `502` / `ai_failed`，两种情况下另外 8 个接口完全正常。这是 PRD 第 11 条验收标准。
6. **支持当前标签页内多轮对话。** 前端通过 `sessionStorage` 缓存并在每次请求中携带最近 10 个完整问答轮次；刷新页面可恢复，关闭标签页后清除。服务端不保存会话，每一轮仍重新检索知识图谱。

### 4.10 `POST /api/ai/ask/stream`

请求体与 `/api/ai/ask` 完全相同，响应类型为 `text/event-stream`。前端使用 `fetch` 读取响应流，不使用只能发起 GET 请求的原生 `EventSource`。

事件顺序：

```text
event: metadata
data: {"retrieved_entity_ids":["gauss-law"],"insufficient_knowledge":false}

event: delta
data: {"text":"高斯定律"}

event: done
data: {"used_entity_ids":["gauss-law"],"insufficient_knowledge":false,"message":null}
```

事件约定：

| 事件 | 数据 | 说明 |
| --- | --- | --- |
| `metadata` | `retrieved_entity_ids`、`insufficient_knowledge` | 每次响应的第一个事件；只有检索命中的知识点，此时还不知道回答会引用哪些 |
| `delta` | `text` | 回答文本片段，可以出现多次 |
| `done` | `used_entity_ids`、`insufficient_knowledge`、`message` | 正常结束。回答全部生成后才统计实际引用的知识点；前端此时才把本轮加入历史 |
| `error` | `code`、`message` | 流开始后的模型错误，出现后不再发送 `done` |

配置缺失发生在流开始前，因此仍返回 HTTP `503`。模型连接或生成错误可能发生在流开始后，此时 HTTP 状态已经是 `200`，通过 `error` 事件报告。知识不足时不调用模型，依次发送 `metadata`、固定回答的 `delta` 和 `done`。

## 5. CORS 与部署

### 5.1 当前配置

```python
allow_origins=["*"]
allow_credentials=False
allow_methods=["GET", "POST"]
allow_headers=["*"]
```

### 5.2 为什么允许全部来源

这是**本地单用户工具**：没有鉴权、没有 Cookie、没有用户数据、监听地址是 `127.0.0.1`。此时限制来源只会制造麻烦——前端既可能用 `file://` 直接打开，也可能跑在 `5173`、`5500` 或别的静态服务端口上，逐一列举必然漏。

原 `main.py` 只允许 `http://localhost:5173`，而实际前端是直接打开 HTML 文件的，来源是 `null`，**浏览器会直接拦掉请求**。这是老版本跑不起来的直接原因之一。

**部署到公网前必须改。** 只要这个服务不再是本机访问，`allow_origins=["*"]` 就要换成明确的域名列表。这一点记在 PRD 阶段五。

### 5.3 端口

统一使用 **8000**。

原项目里 `README.md` 和 `main.py` 写的是 8000，但 `html-learning/app.js` 和 `frontend-learning-plan.md` 请求的是 8001，两边对不上，前端一直连不上后端。本契约明确为 8000，前端代码里的地址必须按这个改。

前端不应把地址硬编码在业务代码里，建议在入口处定义一次：

```js
const API_BASE = "http://127.0.0.1:8000/api";
```

## 7. 启动时的数据校验

知识库在服务启动时加载并校验（设计文档第 16 节，共 19 条规则）。

**校验不通过时服务直接启动失败，不提供任何接口。**

这是刻意的选择：如果带着错误数据启动，错误会在前端渲染时才以「页面空白」「公式显示成乱码」的形式暴露出来，排查成本远高于启动时直接报错。

失败信息必须指出具体位置。校验分两步，先报结构错误，结构全部正确后再报语义错误：

```text
知识库校验失败：5 处错误
  1. entities[6].details.definition（type=law）：缺少这个字段
  2. entities[6].details.key_points（type=law）：缺少这个字段
  3. entities[6].details.common_misconceptions（type=law）：缺少这个字段
  4. entities[6].details.statement（type=law）：该类型不允许这个字段（字段名拼错，或者 type 选错了）
  5. entities[6].details.formula_ids（type=law）：该类型不允许这个字段
```

结构错误修完后再跑一次，才会看到语义层面的错误：

```text
知识库校验失败：5 处错误
  1. chapters[1] (id=electrostatic-field)：order=1 与其他章节重复
  2. entities[0] (id=gradient)：chapter_id='no-such-chapter' 指向不存在的章节
  3. entities[0] (id=gradient)：name 不能为空
  4. relations[0] (gradient --prerequisite--> no-such-entity)：target_id='no-such-entity' 指向不存在的实体
  5. relations[0] (gradient --prerequisite--> no-such-entity)：description 不能为空
```

**为什么要分两步：** 语义校验需要在已解析的对象上跑，而对象解析不过就先拿不到对象。一次全报需要在结构错误时做宽容解析，代码量明显增加，面且实际写数据时不会同时出现两类错误：字段写错之后一般会先改对再继续填内容。

**因此 `/api/health` 不会报告「数据有问题」**——数据有问题时它根本不会响应，前端看到的是连接失败。前端应该把「请求失败」和「返回了错误」都归到同一个错误提示上。
